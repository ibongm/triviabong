
# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start Vite dev server
- `npm run build` — production build to `dist/`
- `npm run preview` — preview the production build locally
- `npm run lint` — run ESLint over the project
- `npm test` — run the Vitest unit suite (`src/**/*.test.js`)

The unit suite covers pure logic only — scoring/leveling/achievements math, question validation/merge, stats merging, category-key resolution — deliberately nothing that touches React rendering, Firebase, or the browser (no jsdom/`@testing-library` dependency). It does **not** verify the app actually works end-to-end (a passing unit suite says nothing about whether a round can be played start-to-finish, or whether Firestore rules still permit a real write). For that, use the `run-triviabong` skill (`.claude/skills/run-triviabong/`): `node golden-path.mjs` starts the dev server and drives the full golden path — lobby → category → leaderboard → quiz → jokers → game-over → save score → stats modal → back to lobby — in headless Chromium, failing on any browser console error (which is how a Firestore rules regression would surface). `node cross-device-sync-check.mjs` separately verifies stats actually follow an account across devices (signs in as the shared `BongBotTest` account in one browser context — creating it if it doesn't exist yet — plays a partial round, logs in with the same credentials in a second fresh context, and asserts the numbers match). `node two-player-match-check.mjs` verifies the 1v1 live-invite match flow (Plan B) with two genuinely distinct signed-in uids in two *concurrently* active browser contexts (both playing at once, via `Promise.all` — not sequentially like the cross-device script) — this is what caught a real race where `player1Answer`/`player1Score` being written as two separate Firestore updates let a reveal/finish transition land before the second write, leaving one player's client with a stale final score; the fix made them one atomic write (see `matches.js`'s `submitMatchAnswer`). **E2E testing uses two fixed accounts, `BongBotTest` and `BongBotTest2`** — the scripts used to mint a throwaway account per run, which accumulated in production and whose generated names exceeded the 20-char `displayName` cap in `firestore.rules`, silently breaking the admin panel's "Popuni sve profile" backfill for every player. See that skill's `SKILL.md` for setup and gotchas — notably, `golden-path.mjs` is a single run-to-completion script rather than an interactive REPL, because a REPL fed via heredoc reliably broke after the first command once Chromium was launched.

**CI.** `.github/workflows/ci.yml` runs `npm run lint` (non-blocking — see the workflow's own comment on pre-existing lint debt), `npm test` (blocking), and `npm run build` on every push/PR. The golden-path E2E check is deliberately *not* in that workflow: it writes a real score to the live production Firestore leaderboard on every run (no emulator wired into CI), so it's wired instead into `.github/workflows/e2e-manual.yml`, triggered only via `workflow_dispatch` (the Actions tab) — run it deliberately, not on every commit.

## Project overview

KvizArena is a client-only React SPA (Vite, no backend/server code) — a Croatian-language trivia quiz game. All UI copy and question content is in Croatian. It deploys to Vercel as a static site; there is no traditional backend, so almost everything that looks like "server logic" (stats sync, leaderboards, admin actions) goes directly from the browser to Firebase. The one exception is `api/questions.js`, a single Vercel serverless function used only by the admin question-upload feature (see "Admin question upload" below) — it exists specifically because the browser can't write back to the repo's bundled JSON itself.

## Architecture

**State machine, split across `App.jsx` + hooks + screens.** There's no router — the app is a state machine driven by one `gameState` value: `LOBBY -> LEADERBOARD -> PLAYING -> GAMEOVER/VICTORY`. `App.jsx` owns the state machine itself plus the core round/answer logic (`resetRoundState`, `handleAnswer`, `handleAnswerTimeout`, jokers, `applyRoundEndRewards`) - this is the one part deliberately *not* further extracted, since it's the single most interconnected block in the app (one `handleAnswer` call touches ~15 distinct pieces of state/refs) and the risk of a subtle scoring/XP bug from a mechanical extraction outweighed the file-size win. Everything genuinely separable already is:
- `src/screens/{Lobby,Leaderboard,Playing,GameOver}Screen.jsx` - one props-only component per `gameState` render branch. When extending game flow, add a new `gameState` value and a corresponding screen component rather than introducing routing.
- `src/hooks/useOneVsOne.js` - the whole Plan B 1v1 invite/match slice (see "1v1 live match" below).
- `src/hooks/useDailyChallenge.js` - Daily Challenge state/effects. Does *not* own `startDailyChallengeAttempt`/`submitDaily`, which stay in `App.jsx` since they're shared crossroads with the non-daily round path (`resetRoundState`, `saveScore`).
- `src/hooks/useScoreSaving.js` - `saveScore`/`submitDaily`/`handleSaveScore`, the sign-in auto-save effect, and `scoreSaved`/`isSaving`/`autoSaveFailed`/`roundHighlight` state.
- `src/hooks/useGameRound.js` - the pre-existing hook owning the moment-to-moment round state (`score`, `lives`, `streak`, `currentIndex`, timers) that `handleAnswer` reads/writes.

These hooks follow `useGameRound`'s existing "lift state, hand back raw setters" convention (not encapsulated internally) rather than exposing only actions - `App.jsx`'s remaining orchestration functions call the returned setters directly (e.g. `resetRoundState` calls `useScoreSaving`'s `setScoreSaved`/`setRoundHighlight` and `useDailyChallenge`'s `setDailySubmitResult`). `useOneVsOne`/`useDailyChallenge`/`useScoreSaving` are this codebase's first hooks to take more than a couple of primitive params (`useOneVsOne(currentUser, setGlobalStats)`, `useScoreSaving({ ...12 named fields })`) - a deliberate departure from `useGameRound`/`useSessionTracking`/`usePresence`'s no-params-or-primitives-only style, needed because these hooks each genuinely depend on that many independent pieces of `App.jsx`'s state.

Each question gets `QUESTION_TIME_SECONDS` (currently 20) to answer — a single named constant near the top of the file, not a magic number repeated at each of the 5 places `timeLeft` gets reset.

**Question data.** Questions live as static JSON files under `src/data/categories/*.json` (one file per category, Croatian question/answer text, shape `{ id, category, question, correct_answer, incorrect_answers[] }`). `src/data/questionsLoader.js` is the only access point (`getQuestionsByCategory`, `getAllCategories`, `getAllQuestions`, `getRawCategoryQuestions`) and resolves aliases via `resolveCategoryKey`/`CATEGORY_ALIASES` in `src/data/categoryKeys.js` (kept separate from `questionsLoader.js`, which is the only file that actually imports the JSON, so `api/questions.js` can resolve category keys without pulling ~500KB of question data into its serverless bundle) — this reconciles mismatches between JSON filenames, internal pack keys, and category keys used elsewhere in the app (e.g. the file `znanost_i_tehnologija.json` and key `science` both resolve to pack key `znanost`; `knjizevnost_i_umjetnost.json` resolves to `knjizevnost`). When adding a category, add the JSON file, register it in `questionsLoader.js`'s `CATEGORY_FILE_LOADERS` map (a lazy `import()` per category, see "Code-splitting and bundle size" below) and in `categoryKeys.js`'s `PRIMARY_CATEGORIES` (which also supplies the category's label/icon, and is `getAllCategories()`'s source of truth for the key list), and add any alias spellings to `CATEGORY_ALIASES` — `CATEGORY_META` (both `App.jsx` and `StatsModal.jsx` import from it) is derived from `PRIMARY_CATEGORIES` automatically.

**Opće znanje is an aggregate pool, not its own deck.** `getQuestionsByCategory('opca_znanje')` returns `getAllQuestions()` (every category's questions combined) rather than just the ~100 questions in `opca_znanje.json` — see `AGGREGATE_CATEGORIES` in `questionsLoader.js`. This means questions added to *any* category automatically enrich Opće znanje too. Because of this, the quiz header in `App.jsx` shows each question's own `category` field (resolved through `getCategoryDetails`) during play, rather than the selected category's label — otherwise every question in an Opće znanje round would misleadingly show "Opće znanje" regardless of where it actually came from. Tooling that needs a category's *own* file contents (the admin upload preview) must use `getRawCategoryQuestions`, which bypasses the aggregate behavior — using `getQuestionsByCategory('opca_znanje')` there would incorrectly compare against all 1492 questions instead of the ~100 actually in that file.

**Admin question upload.** `AdminPanel.jsx` has a "Dodaj Pitanja" section: the admin drops a `.json` file, it's validated and previewed client-side (`src/utils/questionMerge.js` — `validateQuestions`/`detectCategory`/`mergeQuestions`), then submitted with a Firebase ID token to `api/questions.js`, a Vercel serverless function. That function re-validates independently (never trusts the client preview), then merges via the GitHub Contents API: reads the target category file, merges in only genuinely new questions (skips anything matching an existing id or normalized question text — uploads never delete or overwrite), and commits the result to `main`, which triggers Vercel's normal auto-deploy (~1-2 minutes). `src/utils/questionMerge.js` has no React/Firebase imports specifically so both the browser (preview) and the serverless function (authoritative merge) run the identical logic — if they ever diverge, the preview could show a different outcome than what actually lands.

Requires three env vars set in Vercel (Project Settings → Environment Variables, both Production and Preview): `GITHUB_TOKEN` (a fine-grained GitHub PAT scoped to just this repo, *Contents: read and write* permission — **not** prefixed `VITE_`, or it would get inlined into the client bundle), `GITHUB_REPO` (`ibongm/triviabong`), and `GITHUB_BRANCH` (`main`). Without `GITHUB_TOKEN`/`GITHUB_REPO` set, the endpoint responds 500 rather than silently failing. Auth is verified with `jose` against Google's public Firebase JWKS (no service-account key needed) — the token's `email` claim must match the same hardcoded `ADMIN_EMAIL` used elsewhere (see "Admin panel" below).

`npm run dev` (Vite) does **not** serve `/api/*` — there's no dev-time equivalent of the Vercel Functions runtime wired in. To exercise `api/questions.js` locally, use `npx vercel dev` (after `npx vercel env pull` to get the env vars above into `.env.local`).

**Firebase (`src/services/firebase.js`).** Provides Auth (Google + email/password) and Firestore for: user profile/stats (`users/{uid}`), and per-category leaderboards (`leaderboards/{category}/scores`). Firebase config/API key is committed in this file — it's a public client-side Firebase key (expected for this SDK), not a secret. Player stats (the full shape in `src/constants/defaultGlobalStats.js` — level/xp/coins plus totalGames/totalAnswered/totalCorrect/maxStreak/totalScore/categoryStats) are cached in `localStorage` (`triviabong_global_stats`, `triviabong_leaderboards`) and synced to Firestore via `syncUserStatsToFirestore` when a user is signed in, so stats follow the account across devices; anonymous play works entirely off localStorage. Leaderboard behavior lives inline in `App.jsx` plus `firebase.js`.

**Stats-read race (`getUserStatsFromFirestore`).** On login, `AuthModal.jsx`'s `syncUserProfile()` write and `App.jsx`'s `onAuthStateChanged`-triggered stats read are two separate, unsequenced reactions to the same auth event — on a brand-new client (first login on that device), the profile write can get locally queued *while* the stats read is already in flight, and the read comes back reflecting only that pending write's fields (`hasPendingWrites: true` even on a server fetch), not the full stats another device already synced. `waitForPendingWrites()` called *before* the fetch doesn't help (nothing is pending yet at that point — classic TOCTOU); the fix checks `docSnap.metadata.hasPendingWrites` *after* fetching and only then waits + refetches. Found via `cross-device-sync-check.mjs` failing consistently regardless of added delay (ruled out as a timing issue) — see that function's comment for the full trace.

**Code-splitting and bundle size.** `App.jsx` lazily loads `AdminPanel.jsx` via `React.lazy`/`React.Suspense` (~12KB gzipped, deferred until an admin actually opens it). `questionsLoader.js` dynamically `import()`s every category JSON behind a cached module-level promise (`loadPacks()`), grouped into one `questions-data` chunk (~345KB gzipped) by `vite.config.js`'s `manualChunks` rule — so it's fetched once, lazily, on first use rather than eagerly. Every export except `getAllCategories()` (which only needs the 8 key strings, sourced from `categoryKeys.js`'s `PRIMARY_CATEGORIES` rather than the JSON, so it stays synchronous and JSON-free — the lobby renders without loading any question data at all) is therefore `async`: `getQuestionsByCategory`, `getAllQuestions`, `getRawCategoryQuestions`, plus the new `getAllCategoryPacks` (bulk accessor for admin tooling, which needs every category's contents at once). Callers await accordingly — round start (`launchQuizRound`), Daily Challenge start, 1v1 match creation (`matches.js`'s `createMatch`) and match rendering (`MatchView.jsx`, which resolves questions in an effect rather than a render-path `useMemo`) all do. Eager first-paint payload dropped from ~616KB gzipped to ~272KB gzipped (main bundle + vendor-ui + runtime + CSS) as a result — confirmed in a real browser's Network tab: loading the lobby or a category leaderboard fetches zero question data; only starting a round triggers the `questions-data` chunk request.

**Admin panel.** The UI gate is client-side: `ADMIN_EMAIL` is hardcoded in `App.jsx` (`ivanm.ploce@gmail.com`). When signed in as `ADMIN_EMAIL`, an Admin button appears in the header to open the panel, and visiting the `/admin` path directly opens the panel automatically (via `isAdminPath()` in `App.jsx`). `AdminPanel.jsx` manages Firestore user records (edit level/xp/coins/role, delete users) directly from the client. The real authorization boundary is `firestore.rules` (deployed via `firebase deploy --only firestore:rules`, project set in `.firebaserc`) and `api/questions.js` — **if `ADMIN_EMAIL` is ever updated in `App.jsx`, both `api/questions.js` and `firestore.rules` must be updated and redeployed to match, or authorization will fail.** The rules also restrict `users/{uid}` so only the owner or admin can read/write it, block anyone but admin from setting their own `role`, and bound leaderboard score writes to a plausible range (see comments in `firestore.rules` for the derivation). Rule changes should be tested against the Firestore emulator before deploying — `firebase emulators:exec --only firestore "node <test-script>.mjs"` using `@firebase/rules-unit-testing` — since there's no rules test suite checked into the repo; write one ad hoc when validating a rules change. Note the rule's `role` protection is diff-based: an owner write that touches `role` is denied even if it's just dropping the field via a non-merge `setDoc` overwrite — harmless in practice since the app always writes profile updates with `{ merge: true }`, but worth knowing if that pattern ever changes.

**Leveling.** `src/utils/leveling.js` derives `level` from lifetime `xp` (`computeLevelFromXp`, flat `XP_PER_LEVEL = 500`). It's only recomputed at the moment `xp` increases from gameplay (`App.jsx`'s `handleAnswer`), never on login/read, via `level: Math.max(prev.level || 1, computeLevelFromXp(newXp))` — the `Math.max` guard means gameplay can only move level *up*, so an admin's manual override (`AdminPanel.jsx`) survives until the player's own xp organically earns a higher level rather than getting silently reset on their next correct answer.

**Styling.** Tailwind CSS v3 — `src/index.css` uses `@tailwind` directives, `postcss.config.js` runs the `tailwindcss`/`autoprefixer` PostCSS plugins, and `tailwind.config.js` is v3-style. `vite.config.js` only registers the `@vitejs/plugin-react` plugin.

**Sound.** `src/utils/sound.js` is a small singleton wrapping the Web Audio API (`sound.playClick/playCorrect/playWrong/playTick`), lazily creating an `AudioContext` on first use to respect browser autoplay policies.
