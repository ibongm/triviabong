## Commands

- `npm run dev` — start Vite dev server
- `npm run build` — production build to `dist/`
- `npm run preview` — preview the production build locally
- `npm run lint` — run ESLint over the project
- `npm test` — run the Vitest unit suite (`src/**/*.test.js`)

The unit suite covers pure logic only — scoring/leveling/achievements math, question validation/merge, stats merging, category-key resolution — deliberately nothing that touches React rendering, Firebase, or the browser (no jsdom/`@testing-library` dependency). It does **not** verify the app actually works end-to-end (a passing unit suite says nothing about whether a round can be played start-to-finish, or whether Firestore rules still permit a real write). For that, use the `run-triviabong` skill (`.claude/skills/run-triviabong/`): `node golden-path.mjs` starts the dev server and drives the full golden path — lobby → category → leaderboard → quiz → jokers → game-over → save score → stats modal → back to lobby — in headless Chromium, failing on any browser console error (which is how a Firestore rules regression would surface). `node cross-device-sync-check.mjs` separately verifies stats actually follow an account across devices (signs in as the shared `BongBotTest` account in one browser context — creating it if it doesn't exist yet — plays a partial round, logs in with the same credentials in a second fresh context, and asserts the numbers match). `node two-player-match-check.mjs` verifies the 1v1 live-invite match flow (Plan B) with two genuinely distinct signed-in uids in two *concurrently* active browser contexts (both playing at once, via `Promise.all` — not sequentially like the cross-device script) — this is what caught a real race where `player1Answer`/`player1Score` being written as two separate Firestore updates let a reveal/finish transition land before the second write, leaving one player's client with a stale final score; the fix made them one atomic write (see `matches.js`'s `submitMatchAnswer`). **E2E testing uses two fixed accounts, `BongBotTest` and `BongBotTest2`** — the scripts used to mint a throwaway account per run, which accumulated in production and whose generated names exceeded the 20-char `displayName` cap in `firestore.rules`, silently breaking the admin panel's "Popuni sve profile" backfill for every player. See that skill's `SKILL.md` for setup and gotchas — notably, `golden-path.mjs` is a single run-to-completion script rather than an interactive REPL, because a REPL fed via heredoc reliably broke after the first command once Chromium was launched.

**CI.** `.github/workflows/ci.yml` runs two jobs on every push/PR: `lint-and-build` (`npm run lint`, non-blocking — see the workflow's own comment on pre-existing lint debt; `npm test` and `npm run build`, both blocking), and `e2e`, which runs the three E2E Playwright scripts (`golden-path.mjs`, `cross-device-sync-check.mjs`, `two-player-match-check.mjs`) against the Firebase Emulator Suite. The `e2e` job installs a JDK (`actions/setup-java@v4`, Temurin 21 — `firebase-tools`' emulators require 21+), starts the Firestore+Auth emulators (`firebase-tools`, a devDependency), and points the dev server at them via `VITE_USE_FIREBASE_EMULATOR=true` (read in `src/services/firebase.js`, which calls `connectFirestoreEmulator`/`connectAuthEmulator` when that flag is set), so runs never touch live production Firestore/Auth or the real leaderboard — `firebase.json`/`.firebaserc` at the repo root configure the emulator ports (Firestore 8080, Auth 9250, UI 4000) to match. `.github/workflows/e2e-emulator.yml` duplicates the same `e2e` job for ad hoc `workflow_dispatch` runs (e.g. against a branch other than the one currently pushing) — keep the two in sync if either changes. Omitting the env var (e.g. running the scripts locally without starting the emulators first) falls back to live production, same as before — see `run-triviabong`'s `SKILL.md` for when that's still the right call.

## Project overview

KvizArena is a client-only React SPA (Vite, no backend/server code) — a Croatian-language trivia quiz game. All UI copy and question content is in Croatian. It deploys to Vercel as a static site; there is no traditional backend, so almost everything that looks like "server logic" (stats sync, leaderboards, admin actions) goes directly from the browser to Firebase. The one exception is `api/questions.js`, a single Vercel serverless function used only by the admin question-upload feature (see "Admin question upload" below) — it exists specifically because the browser can't write back to the repo's bundled JSON itself.

## Architecture

**State machine, split across `App.jsx` + hooks + screens.** There's no router — the app is a state machine driven by one `gameState` value: `LOBBY -> LEADERBOARD -> PLAYING -> GAMEOVER/VICTORY`. `App.jsx` owns the state machine itself plus the core round/answer logic (`resetRoundState`, `handleAnswer`, `handleAnswerTimeout`, jokers, `applyRoundEndRewards`) - this is the one part deliberately *not* further extracted, since it's the single most interconnected block in the app (one `handleAnswer` call touches ~15 distinct pieces of state/refs) and the risk of a subtle scoring/XP bug from a mechanical extraction outweighed the file-size win. Everything genuinely separable already is:
- `src/screens/{Lobby,Leaderboard,Playing,GameOver}Screen.jsx` - one props-only component per `gameState` render branch. When extending game flow, add a new `gameState` value and a corresponding screen component rather than introducing routing.
- `src/hooks/useOneVsOne.js` - the whole Plan B 1v1 invite/match slice (its data flow and rules are documented in the header comments of `src/services/matches.js` and the `matches/{matchId}` block of `firestore.rules`).
- `src/hooks/useDailyChallenge.js` - Daily Challenge state/effects. Does *not* own `startDailyChallengeAttempt`/`submitDaily`, which stay in `App.jsx` since they're shared crossroads with the non-daily round path (`resetRoundState`, `saveScore`).
- `src/hooks/useScoreSaving.js` - `saveScore`/`submitDaily`/`handleSaveScore`, the sign-in auto-save effect, and `scoreSaved`/`isSaving`/`autoSaveFailed`/`roundHighlight` state.
- `src/hooks/useGameRound.js` - the pre-existing hook owning the moment-to-moment round state (`score`, `lives`, `streak`, `currentIndex`, timers) that `handleAnswer` reads/writes.

These hooks follow `useGameRound`'s existing "lift state, hand back raw setters" convention (not encapsulated internally) rather than exposing only actions - `App.jsx`'s remaining orchestration functions call the returned setters directly (e.g. `resetRoundState` calls `useScoreSaving`'s `setScoreSaved`/`setRoundHighlight` and `useDailyChallenge`'s `setDailySubmitResult`). `useOneVsOne`/`useDailyChallenge`/`useScoreSaving` are this codebase's first hooks to take more than a couple of primitive params (`useOneVsOne(currentUser, setGlobalStats)`, `useScoreSaving({ ...12 named fields })`) - a deliberate departure from `useGameRound`/`useSessionTracking`/`usePresence`'s no-params-or-primitives-only style, needed because these hooks each genuinely depend on that many independent pieces of `App.jsx`'s state.

Each question gets `QUESTION_TIME_SECONDS` (currently 20) to answer — a single named constant near the top of the file, not a magic number repeated at each of the 5 places `timeLeft` gets reset.

**Question data.** Questions live as static JSON files under `src/data/categories/*.json` (one file per category, Croatian question/answer text, shape `{ id, category, question, correct_answer, incorrect_answers[], addedOn? }` — `addedOn` is a Zagreb `YYYY-MM-DD` date stamped on every question merged since 2026-10-10; older questions don't have it). `src/data/questionsLoader.js` is the only access point (`getQuestionsByCategory`, `getAllCategories`, `getAllQuestions`, `getRawCategoryQuestions`) and resolves aliases via `resolveCategoryKey`/`CATEGORY_ALIASES` in `src/data/categoryKeys.js` (kept separate from `questionsLoader.js`, which is the only file that actually imports the JSON, so `api/questions.js` can resolve category keys without pulling ~500KB of question data into its serverless bundle) — this reconciles mismatches between JSON filenames, internal pack keys, and category keys used elsewhere in the app (e.g. the file `znanost_i_tehnologija.json` and key `science` both resolve to pack key `znanost`; `knjizevnost_i_umjetnost.json` resolves to `knjizevnost`). When adding a category, add the JSON file, register it in `questionsLoader.js`'s `CATEGORY_FILE_LOADERS` map (a lazy `import()` per category, see "Code-splitting and bundle size" below) and in `categoryKeys.js`'s `PRIMARY_CATEGORIES` (which also supplies the category's label/icon, and is `getAllCategories()`'s source of truth for the key list), and add any alias spellings to `CATEGORY_ALIASES` — `CATEGORY_META` (both `App.jsx` and `StatsModal.jsx` import from it) is derived from `PRIMARY_CATEGORIES` automatically.

**Opće znanje is an aggregate pool, not its own deck.** `getQuestionsByCategory('opca_znanje')` returns `getAllQuestions()` (every category's questions combined) rather than just the ~100 questions in `opca_znanje.json` — see `AGGREGATE_CATEGORIES` in `questionsLoader.js`. This means questions added to *any* category automatically enrich Opće znanje too. Because of this, the quiz header in `App.jsx` shows each question's own `category` field (resolved through `getCategoryDetails`) during play, rather than the selected category's label — otherwise every question in an Opće znanje round would misleadingly show "Opće znanje" regardless of where it actually came from. Tooling that needs a category's *own* file contents (the admin upload preview) must use `getRawCategoryQuestions`, which bypasses the aggregate behavior — using `getQuestionsByCategory('opca_znanje')` there would incorrectly compare against the whole combined pool instead of the ~100 actually in that file. **Don't hardcode a total question count anywhere** — it grows with every admin upload, and a stale figure here caused a real mis-sizing on 2026-08-22 (a doc-per-question cache was sized against a long-outdated "1492" when the real total was 5,949, so a "bounded" admin read turned out to cost ~2,900 reads). Count them if it matters: `node -e "…readdirSync('src/data/categories')…"`.

**Daily Challenge selection must not depend on pool size.** `src/utils/dailySeed.js`'s `selectDailyQuestions` ranks each eligible question by a hash of `(dateKey, question.id)` and takes the lowest 10; a question is eligible only if it has no `addedOn` or `addedOn < dateKey`. The previous implementation seeded-shuffled the *whole* pool, so every question added anywhere (the generator workflow commits — and therefore auto-deploys — several times a day) silently swapped the entire day's set, while everyone still shared one daily leaderboard and payout. Keep both properties if this is ever changed: a question's rank must depend only on its own id and the date, and questions added today must not be eligible today.

**Question generator.** `scripts/generate-questions.mjs` (run by `.github/workflows/generate-questions.yml`) routes Gemini output through the same `validateEntry`/`mergeQuestions` as the admin upload, dedupes against the **whole bank** (`buildQuestionTextIndex` over every other category file, not just the target), uses `ID_PREFIXES`, and stamps `addedOn`. It previously wrote straight to the file with its own prefixes, which is where the 40 `hr_his_*` and 80 `hr_spo_*` ids (instead of `hr_hist_`/`hr_sport_`) and most of the bank's duplicate questions came from — those ids are left as-is since `questionStats`, matches and reports reference them. `--dry-run` prints what would be added. `scripts/report-duplicate-questions.mjs` lists existing exact duplicates (read-only; removal is a manual decision). Any tool that rewrites a category file must preserve fields it doesn't know about (`addedOn`, and later `explanation`/`difficulty`) — `editQuestionById` and `audit-category.mjs` both spread the original entry for that reason.

**Shuffling.** Use `shuffleArray` from `src/utils/questionUtils.js` (Fisher–Yates). Never `sort(() => Math.random() - 0.5)`: it isn't uniform, and because `getQuestionOptions()` lists the correct answer first, it put the correct answer in position A ~36% and D ~31% of the time.

**Feature flags.** `src/constants/features.js` holds one boolean per engagement feature (mission fallbacks, explanations, difficulty, async duels, weekly boards, leagues), all `false`. New feature code ships dark behind its flag so it can merge before the Firestore rules it needs are deployed.

**Daily missions.** Schedule in `src/constants/missions.js` (7 days × 3 slots, keyed by the weekday of the Zagreb date key); pure progress logic in `src/utils/missionProgress.js` (`applyMissionEvent`, `applyHybridHalf`, unit-tested); persistence in `src/hooks/useDailyMissions.js` (`users/{uid}/missions/{dateKey}`, owner-only, no field validation in the rules, so new slot fields need no rules change). Every slot that depends on other players or on submitting a question has an optional `alt` (mission fallbacks, behind `FEATURES.MISSION_FALLBACKS`; with the flag off the hook strips all alts). A slot completes when either path hits its own target — `progress` and `altProgress` never add up, and `completedVia` records which. Solo alts are fed by `recordSoloRoundComplete`, called once from `App.jsx`'s `applyRoundEndRewards` for non-daily rounds only. The hook reads/advances a `stateRef`, not the render's `state`: several record calls fire in one handler (category + streak on every correct answer), and closure state made the last write clobber the earlier ones. `CATEGORY_CORRECT` matches through `resolveCategoryKey` because question files carry both spellings of some categories.

**Answer explanations.** Optional `explanation` field on questions (max `EXPLANATION_MAX_LENGTH` = 220, validated by `validateEntry`; the `questionSubmissions` rule mirrors the cap and `rulesCaps.test.js` ties the two). Behind `FEATURES.EXPLANATIONS`. Solo rounds: after every answer/timeout on a question that has one, `App.jsx`'s `scheduleAfterAnswer` holds the transition in `explanationAdvanceRef` until "Dalje"/Enter (`continueAfterExplanation`) instead of the 1.2s/1.0s timers; Daily Challenge never pauses, and 1v1 shows explanations only on the match-over screen. Paused time (explanations and the secret-achievement overlay) accumulates in `pausedMsRef` and is subtracted when `applyRoundEndRewards` captures the round's active duration (`finalRoundElapsedMs`), which is what the score save sends as `elapsedMs` — not "now minus round start" at save time, which used to count game-over-screen time and could push `elapsedMs` past the rules' 200000 cap (rejecting the whole leaderboard write). Backfill: `scripts/generate-explanations.mjs` (workflow `generate-explanations.yml`) drafts into `reports/explanations_<category>_<date>.json` on a new branch, flags answers the model doubts in a `_PROVJERITI.json` file, and never edits category files; `scripts/apply-explanations.mjs <file> [--force]` applies a reviewed file by id (never overwrites without `--force`). `scripts/firestore-rules-explanations.test.mjs` covers the two rules changes (submission `explanation`, report reason `wrong_explanation`).

**Difficulty tiers.** Optional `difficulty` (`easy|medium|hard`), `difficultyAccuracy` (0–1) and `difficultySource` (`stats` = measured, `guess` = generator/uploader estimate) on questions; pure logic in `src/utils/difficulty.js` (thresholds: easy ≥ 75% correct, hard < 45%, measured only from `MIN_ATTEMPTS` = 15 attempts), unit-tested. Only `scripts/compute-difficulty.mjs` writes `stats` — it reads the public `questionStats` collection over Firestore REST (no credentials), updates category JSON in place (preserving every other field; accuracy drift under 3 points with an unchanged tier is not rewritten, to keep diffs/redeploys small) and writes `reports/suspect_questions_<date>.md` for questions under 15% correct (worse than guessing → likely a wrong answer key; reported, never auto-edited). The `compute-difficulty.yml` workflow (manual) pushes to a NEW `difficulty/<run>` branch, never to main. `mergeQuestions` stamps any supplied tier as `guess`; the generator asks Gemini for `difficulty_guess`. Behind `FEATURES.DIFFICULTY`: `src/utils/roundComposer.js`'s `composeRound` builds solo rounds (`launchQuizRound`) as 3 easy / 4 medium / 3 hard ordered easy → hard (untiered questions count as medium, so with no tier data it is the old uniform random pick; a short tier is topped up from the rest), `pickMatchQuestionIds` does the same for the 10 played 1v1 questions (the 11th sudden-death reserve stays a random leftover), and the reveal shows "Točno je odgovorilo N% igrača" for `stats`-sourced questions. `FEATURES.DIFFICULTY_BADGE` adds the tier chip. **Daily Challenge is deliberately untouched** — its set is chosen by `dailySeed.js` and a mid-day tier recompute would reorder it for later players. Scoring is not weighted by tier (decision D1). Admin → Pitanja shows the tier/accuracy chip and a tier filter, including "Sumnjiva".

**Async duels.** `FEATURES.ASYNC_DUELS` (plus `ASYNC_DUELS_ADMIN_PREVIEW`, which shows the UI to the verified admin account only — for the production dry run before general release). A separate subsystem from live 1v1: nothing in `matches.js`, `MatchView.jsx` (apart from calling the extracted `computeDuelAnswerScore` in `gameLogic.js`, numbers pinned by `gameLogic.test.js`), `useOneVsOne.js` or the `matches/` rules was changed. Pure logic in `src/utils/asyncDuel.js` (scoring from the stored answer list, winner/tiebreak, abandoned-run detection, inbox state — unit-tested); `src/services/asyncDuels.js` (one-shot fetches only, **no `onSnapshot`**); `src/hooks/useAsyncDuels.js`; `AsyncDuelScreen.jsx` (new `gameState` value `ASYNC_DUEL`) and `AsyncDuelsModal.jsx` ("Izazovi": random pool, challenge a player, inbox). Data: `asyncDuels/{duelId}` (mode, challenger/opponent, category or `'any'`, 10 `questionIds` picked once by the challenger with `composeRound`, status `open → awaiting_opponent → complete | expired`, `expiresAt` = 48 h) and `asyncDuels/{duelId}/results/{uid}` (`in_progress → done`, `score`, `correct`, `totalTimeMs`, `answers[{c,t}]`, `rewardClaimed`). A run's result doc is created `in_progress` **before** the first question (abandoning still uses the attempt); answers are kept in `localStorage` (`utils/duelProgress.js`) and written once at the end; a run abandoned for 10 min is finalized with the saved answers (rest = wrong). **Rules decision that differs from the original plan:** the other player's result is readable once *your own* run is `done` (not once the parent is `complete`) — otherwise a client dying between "finish my run" and "write the winner" would leave both results unreadable; `finishRun` is therefore two writes (my result, then the parent if the other side is done) and `reconcileDuel` repairs the gap on the next fetch. The `complete` update must carry the winner implied by the two stored results (`getAfter()` in `firestore.rules`; mirrored by `decideWinner`). Rewards: each client claims its own (`markRewardClaimed` first, credit second — a crash loses a reward instead of duplicating it) using `applyOneVsOneWin` (`utils/oneVsOneReward.js`, a copy of what `useOneVsOne` applies — change both if the win reward changes), writes a `matchHistory` entry with `async: true`, and counts as a 1v1 win (D7). Missions: finishing my side → `PLAY_1V1` (`recordAsyncDuelPlayed`); win-based missions are credited when the result resolves (`recordAsyncDuelResolved`). The nightly cron (`api/daily-challenge-payout.js`) also runs `sweepExpiredDuels` (independent, never throws, 500 per run). Needs **three deploys by Bong before the flag**: `firestore.rules`, the composite indexes in `firestore.indexes.async-duels.json` (deliberately *not* wired into `firebase.json` — see Firestore indexes below), and nothing else; test the rules first with `scripts/firestore-rules-async-duels.test.mjs` (also run by both e2e workflows). Not yet written: the Playwright `async-duel-check.mjs` E2E.

**Weekly and seasonal boards.** `FEATURES.WEEKLY_BOARDS` (one flag covers the write path, the Rekordi tabs and the lobby card). Pure logic: `src/utils/periods.js` (ISO week keys on the **Zagreb** calendar, `"2026-W42"`, Monday 00:00 → Sunday 24:00; DST-safe because all date maths is on `YYYY-MM-DD` strings and the only timezone conversion is one `Intl` call; 2026 has 53 weeks, so `2027-01-01` is `2026-W53`) and `src/utils/periodBoards.js` (top-5 insertion, weekly → season roll-up, podium tiers, badge ids) — both unit-tested, including the property that every accepted insertion satisfies the interleaving `firestore.rules` checks. Seasons live in `src/constants/seasons.js` (`SEASONS`: id, `startWeek`, `weekCount`; **Season 1 is provisional: 8 weeks from Monday 2026-10-26 (`2026-W44`) — edit `startWeek` there and in the cron's inlined copy if the launch slips**). Ranking (D3): weekly total = sum of a player's 5 best rounds that week; season total = sum of their 5 best weekly totals. Which rounds count: completed solo rounds and Daily Challenge rounds, signed-in players only (not duels). Data: `weeklyBoards/{weekKey}/players/{uid}` = `{name, s1..s5 (desc), total, updatedAt}`; `seasonBoards/{seasonId}/players/{uid}` = `{name, weeks:{weekKey: weeklyTotal}, total, updatedAt}`; `weeklyBoards/{weekKey}` and `seasonBoards/{seasonId}` themselves are payout metadata (Admin SDK only); `badges/{uid}` = `{items:[...]}` (Admin SDK only — **never put badges on `publicProfiles`**, `syncPublicProfile` overwrites it without merge). Write path: `useScoreSaving.js` calls `recordPeriodScore` (`src/services/periodBoards.js`) fire-and-forget **after** the round's own save succeeded — one transaction reading the weekly (+season) doc and writing only if the round raises the weekly total, so a non-qualifying round costs 1–2 reads and no writes; it never throws and never delays the existing save/retry flow. Differences from the original plan: the weekly doc has no `rounds` counter (counting every round would force a write per round), and the season doc stores a `weeks` map instead of `w1..w5` (an update must know *which* week it raises; rules can't sort a map, so a season `total` is only bounded — create ≤ 5×10000 with exactly one week, update never lowers it and raises it by ≤ 10000). Rules ceiling is the same as the solo leaderboard's (scores are client-computed): a weekly doc must start as one round and each update must be a single top-5 insertion; **rules cannot check that `weekKey` is the current week**. UI: Rekordi modal tabs Tjedno | Sezona | Svih vremena (`components/PeriodBoards.jsx`; the all-time tab is the untouched `RekordiBoards`; weekly is the default tab when the flag is on) with a countdown, top 20, the player's own row pinned with an exact rank (count aggregation, `where total > mine`) and season badges next to names; the lobby shows a one-time "Prošli tjedan" card per week (`hooks/usePreviousWeekSummary.js`, acknowledgment in localStorage, so later opens cost no reads). No composite indexes are needed (single-field `total` ordering). Payouts: `api/daily-challenge-payout.js` → `runPeriodPayouts` (independent of the daily payout, never throws) pays the last finished week's podium once (`weeklyBoards/{weekKey}.paidAt`, checked inside the transaction; ties paid in full; 1st 30 coins + 30 XP, 2nd 15 + 15, 3rd 10 + 10 — D10) and, when that week is a season's last, awards badges `sN_gold|silver|bronze` (podium tiers) and `sN_top10` (first ten positions incl. ties) once (`seasonBoards/{id}.paidAt`; no coins for seasons). It runs every night, not only on Sundays, so a missed Sunday run is caught up. The cron carries **inlined copies** of the week helpers, `SEASONS`, tier/badge logic and reward constants (it can't import from `src/`); `src/utils/periodPayout.test.js` pins every copy against the original and tests payout idempotency against an in-memory fake. Needs **one deploy by Bong before the flag**: `firestore.rules` — test first with `scripts/firestore-rules-weekly-boards.test.mjs` (also run by both e2e workflows; not executable in the authoring sandbox, so it has only run in CI/by Bong). Divisions (plan 5.7) and the "Tjedni pobjednik"/"Sezona: Top 10" achievements are deliberately not built; there is no public-profile screen in the client yet, so badges show only on the season board.

**Private leagues.** `FEATURES.LEAGUES`. Friends' groups with a join code and a weekly table. Leagues require an account (D4); no coins/XP for leagues (plan 6.5). Pure logic: `src/utils/league.js` (code generation with an unambiguous alphabet `A-HJ-NP-Z2-9`, 6 chars, crypto source with rejection sampling; `/liga/CODE` parsing; name/emoji sanitizers; `pickNewOwner`/`planLeave`; `buildWeeklyTable`, `buildDailyRanking`, `lastWeekWinners`; `chunk`) - unit-tested in `league.test.js`. Services: `src/services/leagues.js` (never throws; mutations return `{ok, reason}`; **no listeners** - `loadLeaguePage` does one league-doc read + members + chunked `documentId() in [...]` queries (≤ 30 ids each) on `weeklyBoards/{wk}/players` (this and last week) and `dailyLeaderboards/{date}/scores`, cached 60 s in memory). Hook: `src/hooks/useLeagues.js`. UI: `LeaguesModal.jsx` (list / create / join / league views) and `LeaguePage.jsx` (weekly table with crown for last week's winner, last-played text, "Izazovi" button reusing async duels `challengePlayer(member, ANY_CATEGORY)` + `playDuelById`, daily tab, invite code/link with Web Share, owner settings, leave/delete via `ConfirmModal`); lobby row "Lige"; read-only admin section `components/admin/AdminLeagues.jsx`. The weekly table reads Phase 5's `weeklyBoards` data, so leagues need `FEATURES.WEEKLY_BOARDS` data to show scores (without it the table simply lists members unranked).

Data: `leagues/{leagueId}` = `{name ≤30, emoji ≤8, ownerUid, code, memberCount, createdAt}`; `leagues/{id}/members/{uid}` = `{name ≤20, joinedAt, code}` (immutable - a member's shown name is the one from joining; the table prefers the name on their weekly doc); `leagueCodes/{code}` = `{leagueId, ownerUid, code, name, emoji}`; `users/{uid}/leagues/{leagueId}` = owner-only index `{name, emoji, joinedAt}` (this is "my leagues" - one query, no collection-group). Every multi-doc change is **one client `writeBatch`** tied together in `firestore.rules` with `get`/`getAfter`/`exists`/`existsAfter`: create = league + owner member + code doc (+ index); join = member doc + `increment(1)` on `memberCount` + index (a joiner can't read the league, hence `increment`, and the rules check the delta via `getAfter`); leave/kick = member delete + `increment(-1)`; owner leaving hands over to the longest-standing member first (`pickNewOwner`), the last member leaving deletes the league. Only `get` is allowed on `leagueCodes` (no list), so codes can't be enumerated; a join must present the league's *current* code, so regenerating the code locks out stale links. Max 50 members is enforced in rules; max 5 leagues per player is **client-only** (rules can't count a user's leagues).

Invite link `/liga/CODE`: no router, so `useLeagues` parses it once on load, parks the code in `sessionStorage` (`triviabong_pending_league_code`) and `history.replaceState`s the address bar back to `/`. The modal opens once auth has settled (`linkReady`: a user exists or 1500 ms passed); a signed-out visitor sees "Prijavi se" and the code survives the sign-in. Invalid codes (e.g. containing `0`/`O`/`1`/`I`) are ignored.

Deviations / notes: `leagueCodes` also carries `name` and `emoji` (plan didn't) so a joiner can preview the league before joining. Invite code and link are shown to every member, not only the owner. Kicked members' index docs self-clean when they next open the league (permission-denied → "Ukloni s popisa"). Admin delete leaves orphan member docs (invisible once the league doc is gone). Rules can't count non-BMP characters reliably, so the client caps names by UTF-16 length. Codes are brute-forceable only at ~1e9 attempts. No new composite indexes. Needs **one deploy by Bong before the flag**: `firestore.rules` - test first with `scripts/firestore-rules-leagues.test.mjs` (also run by both e2e workflows; **not executable in the authoring sandbox**, so it has only run in CI / by Bong). Not built: the Playwright E2E for leagues, a league achievement, league-vs-league play.

**Firestore indexes.** There is no `firestore.indexes.json` in the repo yet; composite indexes (e.g. the one behind `getPlayerBestScoreForCategory`'s `where uid` + `orderBy score`) live only in the Firebase console. Before adding the file, export the live set first (`firebase firestore:indexes > firestore.indexes.json`) — deploying an incomplete file offers to delete every index missing from it. The four indexes async duels need are in `firestore.indexes.async-duels.json` (challenger/opponent inbox queries, the random-opponent pool, the cron's expiry sweep): either create them by hand in the console from that file, or merge them into the exported live file and then add `"indexes": "firestore.indexes.json"` to `firebase.json`.

**Admin question upload.** `AdminPanel.jsx` has a "Dodaj Pitanja" section: the admin drops a `.json` file, it's validated and previewed client-side (`src/utils/questionMerge.js` — `validateQuestions`/`detectCategory`/`mergeQuestions`), then submitted with a Firebase ID token to `api/questions.js`, a Vercel serverless function. That function re-validates independently (never trusts the client preview), then merges via the GitHub Contents API: reads the target category file, merges in only genuinely new questions (skips anything matching an existing id or normalized question text — uploads never delete or overwrite), and commits the result to `main`, which triggers Vercel's normal auto-deploy (~1-2 minutes). `src/utils/questionMerge.js` has no React/Firebase imports specifically so both the browser (preview) and the serverless function (authoritative merge) run the identical logic — if they ever diverge, the preview could show a different outcome than what actually lands.

Requires three env vars set in Vercel (Project Settings → Environment Variables, both Production and Preview): `GITHUB_TOKEN` (a fine-grained GitHub PAT scoped to just this repo, *Contents: read and write* permission — **not** prefixed `VITE_`, or it would get inlined into the client bundle), `GITHUB_REPO` (`ibongm/triviabong`), and `GITHUB_BRANCH` (`main`). Without `GITHUB_TOKEN`/`GITHUB_REPO` set, the endpoint responds 500 rather than silently failing. Auth is verified with `jose` against Google's public Firebase JWKS (no service-account key needed) — the token's `email` claim must match the same hardcoded `ADMIN_EMAIL` used elsewhere (see "Admin panel" below).

`npm run dev` (Vite) does **not** serve `/api/*` — there's no dev-time equivalent of the Vercel Functions runtime wired in. To exercise `api/questions.js` locally, use `npx vercel dev` (after `npx vercel env pull` to get the env vars above into `.env.local`).

**Firebase (`src/services/firebase.js`).** Provides Auth (Google + email/password) and Firestore for: user profile/stats (`users/{uid}`), and per-category leaderboards (`leaderboards/{category}/scores`). Firebase config/API key is committed in this file — it's a public client-side Firebase key (expected for this SDK), not a secret. Player stats (the full shape in `src/constants/defaultGlobalStats.js` — level/xp/coins plus totalGames/totalAnswered/totalCorrect/maxStreak/totalScore/categoryStats) are cached in `localStorage` (`triviabong_global_stats`, `triviabong_leaderboards`) and synced to Firestore via `syncUserStatsToFirestore` when a user is signed in, so stats follow the account across devices; anonymous play works entirely off localStorage. Leaderboard behavior lives inline in `App.jsx` plus `firebase.js`.

**Stats-read race (`getUserStatsFromFirestore`).** On login, `AuthModal.jsx`'s `syncUserProfile()` write and `App.jsx`'s `onAuthStateChanged`-triggered stats read are two separate, unsequenced reactions to the same auth event — on a brand-new client (first login on that device), the profile write can get locally queued *while* the stats read is already in flight, and the read comes back reflecting only that pending write's fields (`hasPendingWrites: true` even on a server fetch), not the full stats another device already synced. `waitForPendingWrites()` called *before* the fetch doesn't help (nothing is pending yet at that point — classic TOCTOU); the fix checks `docSnap.metadata.hasPendingWrites` *after* fetching and only then waits + refetches. Found via `cross-device-sync-check.mjs` failing consistently regardless of added delay (ruled out as a timing issue) — see that function's comment for the full trace.

**Code-splitting and bundle size.** `App.jsx` lazily loads `AdminPanel.jsx` via `React.lazy`/`React.Suspense` (~12KB gzipped, deferred until an admin actually opens it). `questionsLoader.js` dynamically `import()`s every category JSON behind a cached module-level promise (`loadPacks()`), grouped into one `questions-data` chunk (~345KB gzipped) by `vite.config.js`'s `manualChunks` rule — so it's fetched once, lazily, on first use rather than eagerly. Every export except `getAllCategories()` (which only needs the 8 key strings, sourced from `categoryKeys.js`'s `PRIMARY_CATEGORIES` rather than the JSON, so it stays synchronous and JSON-free — the lobby renders without loading any question data at all) is therefore `async`: `getQuestionsByCategory`, `getAllQuestions`, `getRawCategoryQuestions`, plus the new `getAllCategoryPacks` (bulk accessor for admin tooling, which needs every category's contents at once). Callers await accordingly — round start (`launchQuizRound`), Daily Challenge start, 1v1 match creation (`matches.js`'s `createMatch`) and match rendering (`MatchView.jsx`, which resolves questions in an effect rather than a render-path `useMemo`) all do. Eager first-paint payload dropped from ~616KB gzipped to ~272KB gzipped (main bundle + vendor-ui + runtime + CSS) as a result — confirmed in a real browser's Network tab: loading the lobby or a category leaderboard fetches zero question data; only starting a round triggers the `questions-data` chunk request.

**Admin panel.** The UI gate is client-side: `ADMIN_EMAIL` is hardcoded in `App.jsx` (`ivanm.ploce@gmail.com`). When signed in as `ADMIN_EMAIL`, an Admin button appears in the header to open the panel, and visiting the `/admin` path directly opens the panel automatically (via `isAdminPath()` in `App.jsx`). `AdminPanel.jsx` manages Firestore user records (edit level/xp/coins/role, delete users) directly from the client. The real authorization boundary is `firestore.rules` (deployed via `firebase deploy --only firestore:rules`, project set in `.firebaserc`) and `api/questions.js` — **if `ADMIN_EMAIL` is ever updated in `App.jsx`, both `api/questions.js` and `firestore.rules` must be updated and redeployed to match, or authorization will fail.** The rules also restrict `users/{uid}` so only the owner or admin can read/write it, block anyone but admin from setting their own `role`, and bound leaderboard score writes to a plausible range (see comments in `firestore.rules` for the derivation). Rule changes should be tested against the Firestore emulator before deploying — `firebase emulators:exec --only firestore "node <test-script>.mjs"` using `@firebase/rules-unit-testing` — since there's no rules test suite checked into the repo; write one ad hoc when validating a rules change. Note the rule's `role` protection is diff-based: an owner write that touches `role` is denied even if it's just dropping the field via a non-merge `setDoc` overwrite — harmless in practice since the app always writes profile updates with `{ merge: true }`, but worth knowing if that pattern ever changes.

**Leveling.** `src/utils/leveling.js` derives `level` from lifetime `xp` (`computeLevelFromXp`, quadratic curve `xpForLevel(L) = 25 × (L−1)²` since the 2026-08 economy rebalance; XP comes from `XP_PER_CORRECT_ANSWER` plus mode payouts in `src/constants/gameBalance.js`). It's only recomputed at the moment `xp` increases from gameplay (`App.jsx`'s `handleAnswer`), never on login/read, via `level: Math.max(prev.level || 1, computeLevelFromXp(newXp))` — the `Math.max` guard means gameplay can only move level *up*, so an admin's manual override (`AdminPanel.jsx`) survives until the player's own xp organically earns a higher level rather than getting silently reset on their next correct answer.

**Styling.** Tailwind CSS v3 — `src/index.css` uses `@tailwind` directives, `postcss.config.js` runs the `tailwindcss`/`autoprefixer` PostCSS plugins, and `tailwind.config.js` is v3-style. `vite.config.js` only registers the `@vitejs/plugin-react` plugin.

**Sound.** `src/utils/sound.js` is a small singleton wrapping the Web Audio API (`sound.playClick/playCorrect/playWrong/playTick`), lazily creating an `AudioContext` on first use to respect browser autoplay policies.
